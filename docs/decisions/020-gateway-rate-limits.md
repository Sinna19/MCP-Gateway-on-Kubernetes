# 020: Gateway rate limits and closing sessions on access change

Status: accepted (7c parts 1 and 2). Part 2 (chat cap, `/mcp` session cap, sweeps, `last_used_at` throttle) is the last four decisions below.

## Decisions
- **Close sessions when access changes.** Revoking a key (`DELETE /api/keys/:id`) closes the `/mcp` sessions opened with that key; disabling a user or changing their role (`PATCH /api/members/:id`) closes all of that user's sessions. `server.close()` ends the session and every open SSE stream, so no `list_changed` reaches the client. Setting the role a user already has, or re-enabling, closes nothing. The per-request check in `authenticate` stays as the backstop (a revoke done straight in the database). This closes the known gap in ADR 014. A role change closes too because 7e will make the tool list depend on the role.
- **One small limiter we wrote** (`src/rate-limit.ts`, `FixedWindowLimiter`): first take of a key opens a window, at most `max` takes fit, then `Retry-After` is the seconds left, rounded up. `refund`, `reset`, `sweep` and an injectable clock. No library: it is 40 lines I can explain and test with a fake clock.
- **In memory is fine because the gateway is one replica** (ADR 006). Limits are per process; with more replicas each pod would count on its own, so multi-replica would need the counters in Postgres or Redis.
- **Login** (`POST /api/auth/login`): every attempt is counted before the password check, in an IP bucket (default 30) and an email bucket (default 5) per 15 minutes. The email is the same trimmed, lowercased value the lookup uses, so `Admin@X` and `admin@x` are one bucket; unknown emails count too, so the limit does not reveal which exist. Over a limit: 429 + `Retry-After`, even for the right password.
  - A successful login resets the email bucket and refunds its IP token. The IP bucket is never reset, or an attacker could reset it by logging in to their own account between guesses. Refunds matter because dod-check, browser sessions and tests all log in from the same k3d source IP.
  - An attempt refused by the email bucket gives its IP token back, so hammering one known email cannot use up the shared IP budget.
- **`/mcp`**: each `tools/call` message takes one token from the key's bucket (default 60 per minute) before any tool lookup or audit, so unknown tools count too. `initialize`, `tools/list`, GET and DELETE are not counted. Over the limit: HTTP 429 + `Retry-After` + a JSON-RPC error (`-32000`, "rate limit exceeded, retry in Ns").
  - 60/min is far above dod-check (12 requests on its busiest key in a whole run).
- **Client IP**: `trust proxy` is `1`, so `req.ip` is the address Traefik appended to `X-Forwarded-For`. Safe because Traefik overwrites a client-sent value and the NetworkPolicy lets only Traefik reach the gateway (ADR 019). Proved on the cluster: 32 wrong logins with distinct emails and distinct spoofed `X-Forwarded-For: 9.9.9.N` still hit 429 after 30 attempts from the one real IP, and 6 wrong logins for one email with spoofed `1.2.3.N` gave 429 on the 6th.
- **Config** in `charts/gateway/values.yaml` under `limits:` (`login.perEmail`, `login.perIp`, `login.windowSeconds`, `mcp.callsPerMinute`, `mcp.sessionsPerKey`, `chat.dailyCap`), passed as env, read in `src/config.ts` (empty = default, a non-positive or non-integer value fails at start).
- **Daily chat cap** (part 2): each `POST /api/chat` that reaches the LLM path takes one turn from a per-user, per-UTC-day counter, default 200 (`CHAT_DAILY_CAP`). Confirm continuations count too, because each one calls the LLM again. One statement does it, so it is atomic: `INSERT ... ON CONFLICT (user_id, day) DO UPDATE SET count = count + 1 WHERE count < cap RETURNING count`; no row back means refused, and a refused turn is not counted. Refused: 429 + `Retry-After` (seconds to the next UTC midnight) + "daily chat limit reached ... resets at 00:00 UTC", shown by the dashboard as plain text.
  - **Postgres, not memory**: a spend cap must survive a gateway restart (a restart would otherwise hand out a fresh 200), and the conditional upsert is the lock, so two tabs cannot both take the last turn. Table `chat_usage(user_id, day, count)` in migration 004; rows older than 7 days are deleted by the hourly sweep (only today's row is ever read).
  - **One clock**: the UTC day and `Retry-After` both come from the injected `now`, not SQL `now()`, so tests around midnight are deterministic.
  - **Order**: 503 (no LLM) → body validation (a malformed body costs nothing) → the existing one-request-per-user busy check → the cap → the LLM. The cap is the agent's `beforeTurn` hook, called right after the busy check, so a request refused as busy spends no turn, and a confirm refused by the cap keeps its pending entry (still valid after midnight, until its own expiry).
- **`/mcp` session cap** (part 2): an `initialize` while the key already has `mcp.sessionsPerKey` (default 10) open sessions gets HTTP 429 + JSON-RPC `-32000` "too many open sessions for this key (10), close one with DELETE /mcp". No existing session is evicted, so a stolen or buggy client cannot kick out a user's real session by opening new ones. Sessions are counted from the in-memory map, so it is exact for one replica.
  - **Failed handshakes**: a session records `initialized` when the client sends `notifications/initialized` (SDK `server.oninitialized`). The existing 60s sweep closes sessions that are still not initialized more than 60s after creation, so they hold a slot for 60 to 120 seconds at most. The 30-minute idle rule is unchanged.
- **Expired dashboard sessions** (part 2): the same sweep runs `DELETE FROM sessions WHERE expires_at < now()` at most once an hour (the first sweep after start included) and logs the count only. It used to run inside every login; now login does only its insert. Expired rows were never accepted (`findSessionUser` checks `expires_at`), so this only bounds table size.
- **`last_used_at` throttle** (part 2): `findUserByKey` is now a `SELECT`, and the `UPDATE api_keys SET last_used_at` runs only if `KeyUsage` (an in-memory map, one per app) says the key was not written in the last 60 seconds. Revoke forgets the key's entry; the sweep drops old ones. **The dashboard's "last used" is therefore accurate to about a minute.** Authentication itself is unchanged: the revoked/disabled check still hits Postgres on every request.

## Trade-offs
- The per-email limit lets anyone lock a known email out for 15 minutes. Accepted: it expires by itself, and there is no CAPTCHA in scope.
- Limits are per process and reset when the gateway restarts.
- A `/mcp` 429 is an HTTP status plus a JSON-RPC error body, so both HTTP clients and MCP clients see a clear reason.
- The session cap is checked before the new session is registered, so many truly parallel `initialize` calls on one key can overshoot 10 by the width of that race. Accepted: the cap is a guard against runaway clients, not an exact quota.
- The cap check runs before the confirm id and history are validated, so a confirm with an unknown id (404) or a history whose last message is not the user's (400) still spends a turn. Only the schema check (zod) is free.
- A key whose initialize was swept still counts for up to two minutes; a client that retries in a tight loop sees 429 until then.
- Behind k3d's load balancer many local clients share one source IP, hence the higher per-IP number and the per-email limit as the main brute-force guard.
